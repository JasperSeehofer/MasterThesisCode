From Bayes’ Rule to H₀ an interactive discovery book

Chapter 2 — Bayes, Once and For All

One distance and no redshift is not yet an inference — and $N$ events do not sharpen like $\sqrt{N}$.

The failure this chapter answers Chapter 1 ended holding a number and a gap: EMRI-889’s luminosity distance $d_L$ = 88.9 Mpc, measured to a fraction of a percent by general relativity, and a slot marked $z$: unknown. That is not yet an inference. It is not even a statement about $h$. A distance is a measurement; a measurement becomes an inference only when you can say, for every candidate value of the thing you want, how probable this data would have been. This chapter builds that machine — and then discovers that feeding it 1588 real events does not do what you expect.

1. A posterior over one number

Everything in this book is an inference about a single scalar. Write $h$ = $H_0$$\,/\,(100\ \mathrm{km\,s^{-1}\,Mpc^{-1}})$ — dimensionless, and in the mock universe this book runs on it has a true value, $h_{\rm true} = 0.73$ constants.py H. One number. Not a spectrum, not a field, not a 14-parameter waveform: one number, with a truth we are allowed to check against, which is the only reason any of the following chapters can be judged at all.

Bayes’ rule for that one number, given a set of detections $\{x_i\}$, is the thing every reader already knows:

The posterior over $h$ — the project’s own derivation derivations/dark_siren_likelihood.md §1.1 bayesian_statistics.py:1954 evaluate() Schutz 1986, Nature 323, 310 $$ p\bigl(h \mid \{x_i\}\bigr) \;\propto\; p(h)\;\prod_{i=1}^{N} p\bigl(x_i \mid h,\ \mathcal{D}\bigr) $$ with $p(h)$ flat on the analysis grid and $\mathcal{D}$ the statement that the event was detected — the conditioning that Chapter 4 is about ⏭ Ch 4. The pipeline evaluates this on a fixed grid of $h$ values and works throughout in $$ S_N(h) \;=\; \sum_{i=1}^{N} \ln \mathcal{L}_i(h), \qquad \underbrace{\mathcal{L}_i(h)}_{\text{one event, one number per grid point}} \equiv p(x_i \mid h, \mathcal{D}), $$ because a product of 1588 numbers, each of which can be $10^{-7}$, is not a number a computer has. Nothing else in the estimator is additive; this is.

Three design decisions are hiding in that box, and each of them earned its place against a specific failure.

Why a grid and not a sampler. $h$ enters the likelihood only through the distance–redshift map $d_L(z; h, \Omega_m)$, so every event’s expensive part — an integral over candidate host galaxies, which is Chapter 3’s subject ⏭ Ch 3 — can be evaluated once per grid point and cached. A Metropolis sampler would buy nothing: there is no high-dimensional space to explore, and it would pay the same integral per proposal. The production grid has 41 points spanning $[0.60,\,0.86]$, and it is deliberately non-uniform: 0.01-spaced on $[0.60, 0.65]$ and $[0.80, 0.86]$, 0.005-spaced in between. Every integral on this page is a trapezoid over the actual node spacing, and nothing on this page takes a numerical derivative across the seams at 0.65 and 0.80.

Why log-space. Because the naive product underflows. This is not a hypothetical: the project spent Phases 21–23 on it, moved to log-space with four different zero-handling strategies, and recorded the verdict as “fixed, not the cause” ledger #7 H0R:1978 — the bias it was hoped to explain was still there afterwards. Keep that shape in mind; it recurs. The production combiner is combine_log_space() in posterior_combination.py:284-330, and its default zero-handling strategy is physics-floor: an event whose likelihood is exactly zero at some grid points gets those points replaced by its own smallest non-zero value rather than annihilating the whole product.

Why there is no extra $\beta(h)^N$. Each $\mathcal{L}_i$ is already conditional on detection, so the joint posterior is a plain product, with no further population-level selection factor multiplied on top. That is a statement with a citation, not a convenience.

Why the product is plain — the production combiner’s own argument posterior_combination.py:284-330 Loredo 2004 Mandel, Farr & Gair 2019, arXiv:1809.02063 §3 Conditioning on the observed number of detections makes the $\beta(h)^N$ factor of the unconditional (Poisson) likelihood cancel against the rate prior. Applying $-N\log D(h)$ again on top of per-event likelihoods that already carry it is a double count — and the project shipped exactly that for a while, then measured what removing it was worth: it eliminated a $+0.020\ldots+0.025$ shift in $h$ ledger #20 6754ddb.

One more thing the grid has to do, and it is easy to get wrong: it has to be able to hold the answer.

2. Stacking events — and what $\mathcal{L}_i(h)$ costs

Log-additivity has a consequence worth stating before any data arrives: the combined answer cannot depend on the order in which you add events. Addition commutes. Stack the loudest first, stack them alphabetically, stack them in the order they were detected — $S_N(h)$ at $N = 1588$ is the same function every time, to the last bit. This chapter’s generator asserts that rather than asserting it in prose: if the two stacking orders below disagreed at the endpoint by more than $10^{-12}$, the generator would refuse to write its data file.

And yet every partial answer depends on the order completely. That gap — a fixed destination reached by wildly different paths — is where this chapter’s discovery lives. Hold it.

That curve is the whole product this book is building, for one event. And it is expensive in a way that has nothing to do with computers: to know how probable 889’s measured distance is under a given $h$, you need to know what redshift to compare it against. GR gave you $d_L$. It gave you nothing at all about $z$.

The missing ingredient $\mathcal{L}_i(h) = p(x_i \mid h)$ requires connecting a measured $d_L$ to an $h$, and the only bridge is $d_L(z; h, \Omega_m)$ — which needs $z$. The host’s redshift is not measured, not guessed, and not marginalizable with a shrug: it is a discrete latent variable with tens of thousands of candidate values per event, one per catalogued galaxy in the localization volume. Summing over it is Chapter 3. Discovering that the true host is usually not among them is Chapter 5.

3. A vocabulary for “wrong”

Before running anything on 1588 events, the book needs words. “The answer is wrong” is three different diseases with three different cures, and the rest of this book is unreadable without separating them. Each has a one-line operational test — something you could actually run.

Biased
Repeat the experiment many times with the same truth; the mean of the estimates misses truth. Test: $\langle \hat h \rangle - h_{\rm true} \neq 0$ over realizations. Bias is a property of an estimator over realizations, never of one run.
Noisy (scattered)
The estimates spread widely, but their mean is right. Test: the standard deviation of $\hat h$ over realizations is large while the mean is on truth. Curable with more data; bias is not.
Mis-calibrated
The estimates may even be unbiased, but the stated uncertainty is wrong, so the quoted 68% intervals do not contain truth 68% of the time. Test: coverage — the fraction of realizations whose stated interval contains truth. This is the one a project can fail while congratulating itself on the other two.
Pull
The single number that fuses the three: $\text{pull} = (\hat h - h_{\rm true}) / \sigma_{\hat h}$, using the estimator’s own stated $\sigma$. In this project, $\hat h$ is the MAP and $\sigma_{\hat h}$ the posterior standard deviation (score_realistic.py:152). A well-behaved estimator gives pulls that look like draws from $\mathcal{N}(0,1)$.

They are independent. You can build an estimator that fails any one while passing the other two, and the fastest way to believe that is to build one.

Two warnings travel with that table, and both come from the artifact itself.

The ten runs are not ten degrees of freedom. They share two truth universes, so the pulls are strongly correlated within a seed: “two effective degrees of freedom, not ten”. A pull s.d. of 0.58 must therefore not be read as an over-conservative $\sigma$; ten correlated draws cannot estimate a pull dispersion at all. The measured decomposition is that the observation realization contributes sd 0.0055–0.0076 in $h$ within a seed, while the difference between the two truth universes is −0.023 — the realization scatter is the small component.

And no headline may be quoted from this run. The readout’s own amendment, dated 2026-07-30: “Do not quote a headline from EITHER channel of this run.” The reasons need Chapters 5, 8 and 11 ⏭ Ch 11. What this chapter takes from the table is narrower and safe: a working demonstration that bias, scatter and coverage are three separate measurements, and that only the second and third of them can be read off a single run at all.

Trap 2.A — “MAP = truth means the estimator is right.” Chapter 10’s exhibit #49a: a production estimator returned MAP = 0.86 for every injected truth from 0.63 to 0.77, while a catalog_only control tracked truth exactly. It was stable, reproducible, and carried literally zero information about $H_0$. 4. The lurch

Now stack real events. The intuition every reader brings — mine included, before doing this — is that a posterior over 1588 events sharpens like $1/\sqrt{N}$: each event a small, roughly equal contribution, the curve narrowing smoothly, the last hundred events buying about as much as the first hundred. Commit to that intuition before you break it.

Predict, then reveal — how many events carry the answer?

In the idealized campaign-#51 baseline there are 1588 detected events. Rank them by how much each one narrows the combined posterior, and add them up from the top. How many events does it take to reach 90% of the total constraint? Commit, then the Event Stacker below unlocks.

Measured: 24 events. The top 3 alone carry 46% of the in-catalogue budget (47% of the signed total — the two denominators differ by 1.3%, see below), the top 10 carry 71%, the top 20 carry 87%, and 24 of 1588 reach 91%. The cumulative share then overshoots 100% around the 40th event and comes back down, because 466 of the 1588 events have negative curvature — locally they push the other way. The project’s own readout states it as: “100 % of the constraint is carried by the 76 in-catalogue events (4.8 %); the 3 loudest (SNR 995–1425, z ≈ 0.016–0.021) carry 46 % alone. The other ~1510 detections are dark hosts contributing ~1 % of the curvature.” IDEALIZED_BASELINE_READOUT.md:42-47 real: #51 posteriors_fixed If you chose “~1400” you were applying $\sqrt{N}$ reasoning to a sample that does not have $N$ independent things in it. The number that matters is not how many events you have; it is how much information they carry, and that quantity is not spread evenly over anything.
The information statistic used on this page — the project’s own, reused verbatim score_realistic.py:14-21 idealization_audit/audit_information_decomposition.py “How much does event $k$ narrow the posterior” is made precise by the project’s own three-point log-likelihood curvature about truth, $$ c_k \;=\; \ln\frac{\mathcal L_k(0.730)}{\mathcal L_k(0.725)} \;+\; \ln\frac{\mathcal L_k(0.730)}{\mathcal L_k(0.735)}, \qquad \sigma_h \;=\; \frac{\Delta h}{\sqrt{\sum_k c_k}},\quad \Delta h = 0.005 . $$ It is a discrete second difference of $\ln\mathcal L$ taken inside the 0.005-spaced region of the grid, never across a seam. This book does not define an information measure of its own; it reuses this one, because it is the statistic under which every published information number in the project was measured. Measured here: total curvature 238.33, implied $\sigma_h = 3.24\times10^{-4}$ — against the zoom-grid posterior’s $3.00\times10^{-4}$, agreeing to 8%.

With that statistic the concentration is not an impression, it is a count. Of the 1588 events, the 76 whose true host galaxy is actually in the catalogue carry 101.3% of the total; the remaining 1512 carry −1.3%. (Why only 76 of 1588 is Chapter 5’s subject ⏭ Ch 5; here it is simply a label on a subset.) A useful descriptive summary of how uneven the rest is: the participation ratio $\bigl(\sum_k c_k\bigr)^2 / \sum_k c_k^2$ over the 1122 events with positive curvature is 12.1. Eleven hundred events that pull the right way, and the effective count is twelve.

Two things in that widget deserve to be said out loud.

The lurch is real and it is one event. In random order, 222 events have accumulated and the width has moved 13%. The 223rd is EMRI-889, and the width halves in one step, from one galaxy, arriving at no distinguished place in the queue. A posterior plotted only at $N = 1588$ shows you a clean peak and hides the fact that it is three galaxies. That is the entire argument for making this figure interactive: the final answer is not where the information is.

The path is not the destination. Switch the realistic venue to “loudest first” and the running MAP reaches 0.86 — the top of the grid — at the 35th event, sits there for the next thousand, and then walks back down to 0.740, which is exactly where the random order lands. Nothing is wrong with the arithmetic; addition still commutes. What the excursion says is that the loud events and the quiet ones are pulling in different directions, and the answer is where they cross. That is a real, measured feature of this run, it has a name, and it is the subject of Chapter 5 ⏭ Ch 5. Note it and move on — you are not equipped to interpret it yet, and being handed the interpretation now would cost you the discovery.

The failure the next chapter answers Every curve on this page was drawn from delivered per-event likelihoods $\mathcal L_i(h)$ — the one object this chapter never computed. To compute it you must turn a measured distance into a statement about $h$, and that needs a redshift the waveform does not carry. The cheapest source is the galaxy catalogue: look up which galaxies lie inside the localization volume and use theirs. For a typical event that volume contains tens of thousands of them, and not knowing which is the host is not an error bar — it is a sum, and the weights in that sum are astrophysics somebody has to commit to.

Self-check

Q2.1   You add a second event. The combined posterior is the product of the two likelihoods. Under what circumstance does a second event make the posterior worse rather than merely wider?

Show answer
When the second event’s likelihood is biased in a way the first is not, because products of likelihoods are unforgiving: a coherent, same-signed tilt shared across many events accumulates linearly in log-space while the statistical width shrinks as $1/\sqrt N$, so the pull grows as $\sqrt N$. This is precisely the failure mode the book ends with: campaign #53’s 2D channel produces 10 runs all pulling in the same direction at $+4.04\sigma$ REALISTIC_READOUT.md §6. More data made the wrongness more significant, not less.

Q2.2   In the idealized baseline, 76 of 1588 events carry 100% of the constraint and 3 carry 46%. What does that do to your intuition about the estimator’s robustness?

Show answer
It destroys the comfort of large $N$. With effectively ~3–76 informative events, the posterior inherits the idiosyncrasies of a handful of galaxies: their redshift errors, their catalogue masses, their sky positions. A single event’s misbehaviour can then move the answer, which is exactly what the project measured for event 889 — its channel contribution swings $+1.98 \to -2.04 \to -3.30$ across three noise realizations of the same event list, flipping the sign of its whole class’s contribution in one of them CLAIM_2D_BIAS_20260730.md:155 c3c4_allruns_summary.md:123.

Q2.3   Distinguish, with a one-line operational test each: a biased estimator, a noisy estimator, and a mis-calibrated estimator.

Show answer
Biased: repeat the experiment many times with the same truth and the mean of the estimates misses truth. Noisy: the estimates scatter widely but their mean is right. Mis-calibrated: the estimates may even be unbiased, but the stated uncertainty is wrong, so the 68% intervals do not contain truth 68% of the time. The three are independent, and Chapter 10 exists because a project can be congratulating itself on the first while failing the third.

Q2.4   Why does this pipeline evaluate the posterior on an h-grid rather than sampling it?

Show answer
Because every event’s likelihood requires an expensive integral over candidate hosts, and $h$ enters only through the $d_L \leftrightarrow z$ mapping, so the same host set can be re-evaluated at a fixed list of $h$ values and cached — $h$ is one scalar, not a high-dimensional space needing MCMC. The cost is that the grid must resolve the peak: the idealized posterior’s $\sigma_h = 0.00030$ is ~15× narrower than the production grid’s 0.005 step, which is why the un-zoomed posterior looked like a delta spike and why the project needed a zoom-grid hook IDEALIZED_BASELINE_READOUT.md:36-39 — you can see both renderings of the identical posterior in this chapter’s first widget.

Q2.5 (transfer)   You have a posterior machine and a distance. To get a likelihood $p(d_i \mid h)$ you must connect $d_L$ to $h$. Write down the missing ingredient and predict how many candidate values of it a typical event will offer.

Show answer
The host redshift; and typically tens of thousands of candidates, because the localization volume of even a well-localized EMRI contains that many catalogued galaxies. The likelihood must therefore marginalize over “which galaxy”, which is Chapter 3 — and the fact that the answer is usually “none of them” is Chapter 5.
