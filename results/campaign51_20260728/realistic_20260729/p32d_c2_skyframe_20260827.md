## 2. GENERATOR SIDE

File: `darksiren_emri/validation/correspondence_1d.py`.

### 2a. Sky is isotropic where hosts are NOT drawn from the real catalogue

`draw_isotropic_sky` (`:1502-1519`) draws `phiS ~ U(0,2π)`, `cos(qS) ~ U(-1,1)` — genuinely
isotropic. It backs two arms:

- **B-OUT** (`draw_population_redshifts`, bare population draw, `:858-946` region) — `:2017-2018`:
  `host_z = draw_population_redshifts(...)`, `host_phiS, host_qS = draw_isotropic_sky(rng, n)`.
- **B-SEL** (`draw_selected_population_redshifts`, AMENDMENT A-3, `:947-990`) — `:2030-2033`, same
  pattern. Its density is `selected_population_z_weights` (`:897-943`):
  ```
  f_bar = np.asarray(completeness.f_bar(z_arr, h), dtype=np.float64)   # :940
  ...
  w = w_pop * (1.0 - f_bar) * s_interp                                  # :943
  ```
  i.e. **sky-averaged** `f̄`, isotropic sky. These arms represent the "not tied to a real catalogue
  host" population/completion draws — by construction they have no real sky location to condition
  on, so `f̄` + isotropic sky is the textbook Gray et al. (2020/2022) completion-leg treatment (see
  §4).

### 2b. The catalogue-selected 2D venue (the one actually implicated in [P3-2D]) is per-pixel throughout

```python

host_qS_batch = pool.qS[host_idx_batch]
```

Every completeness lookup in this path is **per-pixel**, keyed off that real position:

- **Host draw weight** (`catalogue_selected_host_draw_weights`, `:1343-1385`) calls
  `kernel_smeared_survival` (`:1245-1341`), which at `:1328` does
  `host_pixels = _host_pixels(completeness, host_phiS, host_qS)` and folds per-pixel `f_k` in via
  `_kernel_w_pop_eff` (`:1204-1238`):
  ```python

  ```

  `host_pixels = _host_pixels(completeness, host_phiS, host_qS)` (`:1488`) and builds each host's

**No `f_bar` call appears anywhere in this code path.** `f̄` is confined to the B-OUT/B-SEL
completion-population arms (§2a); the catalogue-selected arm is per-pixel `f_k` end to end.

### 2c. One adjacent observation, NOT part of C2, flagged for completeness

The z-draw density's `S_bar_phi(z;h)` table (`precompute_phi_marginal_survival`,
`bayesian_statistics.py:1947-1994`) is built at a fixed reference angle
(`:1974-1977`, *"the with-BH object is isotropic by standing decision ... phi = theta = 0 here

`host_qS` into the Bernoulli step is a no-op — both applications of the with-BH survival are
**consistently sky-marginalized by the same standing decision (D-02 / gate ii-e, bound
`Sigma^3D(sky)/Sigma^3D(iso) = 1.000202`)**. This is a *detection-probability* sky question, not a
*completeness* sky question — a different quantity from C2's `f̄` vs `f_k`, included here only so a
future reader does not mistake it for the same mechanism.

## 3. ESTIMATOR SIDE

Files: `darksiren_emri/bayesian_inference/bayesian_statistics.py`,
`darksiren_emri/galaxy_catalogue/pixel_completeness.py`.

The estimator draws its host-pixel machinery from the **exact same module** as the generator:


`from_cache_or_build` (`pixel_completeness.py:514`) loads ONE frozen, package-committed
`.npy` file (`M_TH_CACHE_PATH`, `pixel_completeness.py:101-103`), and the module's own docstring
states the design intent and its enforcement explicitly:

```

The sky-average f_bar(z,h) ... is the Omega-marginalized completeness used by the
run-level selection integrals beta_Gbar and the injection fraction F; the per-pixel
f_k is used by the per-event completion numerator B_num (at the event pixel) and by
the joint dark-host sampler W_k (over all pixels).
```
```

HARD CONSISTENCY REQUIREMENT (C1): ONE frozen cached m_th[npix] .npy map is the
SOLE source of f and is loaded byte-identically by BOTH the EMRI injection and the
H0 inference. Any divergence in realization / nside / null-policy gives
f^inj != f^inf and a DIRECT H0 bias.
```

Production's per-event catalogue term (`L_cat`) uses per-pixel `f_k` via the same
`_host_pixels`/`_completeness_at_host_nodes` machinery the generator calls:

```python
# bayesian_statistics.py:554, :571 (definitions); :6939-6940 (catalogue-leg use)
host_pixels = _host_pixels(completeness_model, host_phiS, host_qS)
f_host_den = _completeness_at_host_nodes(completeness_model, y_den, host_pixels, h)
```
and again for the with-BH numerator at `:7357-7361` (`f_host_bh = _completeness_at_host_nodes(...)`).

Production's population-level normalization (`beta_Gbar`, `beta_G_phi`/`beta_Gbar_phi`) uses
sky-averaged `f_bar`, e.g.:

```python
# bayesian_statistics.py:2086, :2088-2089
f_bar = np.clip(np.asarray(completeness.f_bar(z_grid, h), dtype=np.float64), 0.0, 1.0)
beta_G_phi[h] = float(np.trapezoid(f_bar * s_phi * p_pop, z_grid))
beta_Gbar_phi[h] = float(np.trapezoid((1.0 - f_bar) * s_phi * p_pop, z_grid))
```

**This is the identical division of labour the generator uses** (per-pixel `f_k` for per-event/
per-host terms, sky-averaged `f̄` only for population-level normalizations that by construction
don't condition on a specific host location) — enforced by sharing one object, not by two
independent re-implementations that happen to agree.

One estimator-only refinement exists: a `_sky_aware_selection_available` branch
(`bayesian_statistics.py:1062-1081`) that, for the **no-BH-mass (3D)** selection integral only,
replaces the isotropic `(1-f̄)` fallback with a per-pixel, ecliptic-latitude-BAND-resolved
`f_pixels` sum (`:1413-1434`) whenever both the completeness object exposes `pixel_centers`/
`f_pixels` and the detection-probability object exposes `survival_per_band`/`band_edges_sin_beta`.
This "Change 1-4" sky-resolved path applies to the **3D (no-BH-mass) leg**, not the with-BH 2D leg
implicated in [P3-2D]; the with-BH leg is isotropic by the separate, already-bounded D-02/gate
(ii-e) standing decision (§2c). The generator has no analogous 3D-leg sky-band arm — but the 3D leg
is also not the one under investigation here, so this asymmetry is noted, not chased.

## 4. IS THERE A GENUINE MISMATCH?

**No, for the catalogue-selected 2D venue implicated in [P3-2D].** Working through the task's own
"what would have to be true for them to agree" check:

- *If the generator draws hosts FROM the catalogue, sky structure is inherited implicitly* — this
  is exactly what happens (§2b): `pool.phiS`/`pool.qS` come straight from the reduced catalogue's
  real ecliptic columns (`:738`), and every completeness lookup on this path is per-pixel `f_k` at
  that real position. The "isotropic framing" the searcher worried about applies only to the
  **B-OUT/B-SEL completion-leg** arms, which represent galaxies with no catalogue counterpart by
  construction — there IS no real sky position to condition on for those, so `f̄` + isotropic sky is
  not an approximation of something better, it is the exact marginal (`f̄(z) := (1/N_pix) Σ_k
  f_k(z)`, `pixel_completeness.py:275-290`) of the very same per-pixel function, verified below.
- The estimator mirrors this split exactly (§3), and does so via ONE shared, cache-pinned object
  (`from_cache_or_build`), not two independent implementations — so a divergence would require the
  *shared* function itself to disagree with itself, which is definitionally impossible.

**A genuine, narrower issue exists — but inside the estimator alone, not between generator and
estimator.** `docs/derivations/bscale_completion_normalization.md` §4 (2026-08-19) documents:

> "B_num's completeness deficit uses the sky-banded f_k(z) while β_Ḡ^φ uses the isotropic f̄(z).
> That IS a real (numerator vs denominator) population inconsistency ... This item joins the
> D3/F10 J_α point-vs-kernel entry on the tilt ledger as a documented, bounded, unmeasured term."

This is the estimator's own completion-leg numerator (`B_num`, per-pixel `f_k`) vs its own
completion-leg denominator (`β_Ḡ^φ`, sky-averaged `f̄`) — an internal numerator/denominator
mismatch, not a generator/estimator one, and it was flagged in the same memo as *"a separate,
bounded item"*, distinct from the B_scale defect the memo was actually about.

## 5. MAGNITUDE BOUND

**Direct Jensen-gap check (this session, banked cached completeness map).** Since `f̄` is defined
as the exact per-pixel average of `f_k` over the SAME frozen map both sides load
(`pixel_completeness.py:275-290`), `E_pixel[1-f_k(z)] / (1-f̄(z)) ≡ 1` identically over the full
12,288-pixel map by construction — confirmed numerically this session
(`M_TH_CACHE_PATH = darksiren_emri/galaxy_catalogue/m_th_map_nside32.npy`, `h=0.73`):

| z | f̄(z) | E[1−f_k] over ALL 12,288 pixels | ratio |
|---|---|---|---|
| 0.10 | 0.7088 | 0.2912 | 1.0000 |
| 0.20 | 0.4341 | 0.5659 | 1.0000 |
| 0.30 | 0.1916 | 0.8084 | 1.0000 |
| 0.40 | 0.0547 | 0.9453 | 1.0000 |
| 0.50 | 0.0096 | 0.9904 | 1.0000 |
| 0.65 | 0.0003 | 0.9997 | 1.0000 |

(Restricting the average to the 11,537 non-empty/non-ZoA pixels instead of all 12,288 moves the
ratio to 0.84–1.00 across the same z range — purely a statement about which pixel set the average
runs over, not a generator/estimator disagreement; `f̄` is documented to run over ALL `N_pix`
including empty ones, `pixel_completeness.py:277`, and both sides use that same definition.)

**This confirms there is no hidden Jensen gap available to exploit here** — not because the
per-pixel and sky-averaged quantities happen to be numerically close, but because they are
*algebraically* the same object evaluated two ways, on both sides, from the same file.

**The one numeric ceiling that DOES exist** for a completeness-sky-treatment residual in this
codebase is the estimator-internal item from §4: **≲2×10⁻⁴ (≲0.02%)**, per
`BIAS_HISTORY_LEDGER.md` row #133 (*"residual = event-ensemble × completeness sky covariance ≲
2e-4, gate (ii-e)"*) — reusing the `Sigma^3D(sky)/Sigma^3D(iso) = 1.000202` bound from
`docs/derivations/PROPOSAL_2D_SELECTION_FUSION_VERIFIER_ADDENDUM_20260817.md:77-78` (MINOR-5),
which was itself measured for a DIFFERENT quantity (prior-marginal vs likelihood-weighted survival
sky part). **I did not find, in this session's sweep, the actual derivation connecting that bound
to the f_k-vs-f̄ numerator/denominator item** — the ledger's closure line asserts it "by derivation"
but the derivation memo itself (`bscale_completion_normalization.md` §4, same day) still calls the
item "bounded, unmeasured." Flagging this as a soft spot in the prior record (in the spirit of
"verifier output is evidence, not authority") rather than smoothing it over: **the ≲2×10⁻⁴ number
should be treated as the best documented ceiling, not as an independently re-derived one.** Either
way, at ≲0.02% it is roughly two to three orders of magnitude too small to be the task's
unattributed ~×2.5 factor, and 100–1000× too small even relative to the already-small (13.5–16%)
established S̄_φ double-application defect.

## 6. CHEAPEST DECISIVE TEST

Given the code-level finding (§2–§4) is already about as decisive as static reading gets — one
shared object, one frozen file, byte-identical construction call on both sides — the cheapest test
that would add anything is not a new measurement but a **guard against silent future drift**:

1. A one-line runtime parity assertion, mirroring the existing pattern at
   `correspondence_1d.py:1388-1437` (`_verify_rate_weight_parity`): assert that
   `id(completeness_generator) `'s backing `m_th` array and `completeness_estimator`'s backing
   `m_th` array are byte-identical (`np.array_equal`), executed once per harness run. This directly
   operationalizes the module's own "HARD CONSISTENCY REQUIREMENT (C1)" comment
   (`pixel_completeness.py:39-43`) as code rather than prose.
2. If the author wants the *estimator-internal* §4 item (B_num f_k vs β_Ḡ^φ f̄) actually measured
   rather than argued by analogy: re-run the SAME banked-data counterfactual technique
   `bscale_completion_normalization.md` §5 already used for B_scale (swap `β_Ḡ^φ`'s `f̄(z)` for a
   per-pixel-band `f_pixels`-weighted sum — the machinery already exists at
   `bayesian_statistics.py:1413-1434` for the 3D leg — and read the 2D-mean shift off the existing
   banked seeds, zero new compute). This would convert "bounded, unmeasured" into an executed
   number and resolve the §5 soft spot, but it is **not** needed to close out C2 itself, since C2 is
   about generator/estimator agreement, which is not in question here.

Neither test is needed to reach the C2 verdict; both are offered as low-cost hardening/closure
moves for the adjacent items this screen surfaced.

## 7. Summary for the parked [P3-2D] thread

C2 is **REFUTED** as a generator/estimator mismatch: both sides call the identical, cache-pinned
`CompletenessModel` object, and both follow the same documented per-event-`f_k` /
population-level-`f̄` split — the generator's catalogue-selected 2D venue (the one actually
implicated in the parked residual) uses per-pixel `f_k` at the real, catalogue-inherited host sky

anywhere on that path. The Jensen gap the task asked to bound is identically 1.0000 by construction
(§5), not merely small. A distinct, narrower, already-bounded-at-≲0.02% item exists purely inside
the estimator's own completion-leg mixture (numerator `f_k` vs denominator `f̄`) — too small by 2-3
orders of magnitude to own the ~×2.5 unattributed residual, and not a candidate that would explain
why the [P3-2D] repair leaves ~69-70% of the deficit surviving. **C2 does not merit opening as a
thread.**
