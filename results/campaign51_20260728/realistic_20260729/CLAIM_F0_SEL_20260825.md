# CLAIM INTAKE — [F0-SEL] the analysis-intake distance-error cut vs the selection normalization

**STATUS: DRAFT — stage-0 claim intake (measurement-before-gate, row #188 item 2). Read-only
code trace + zero-`evaluate()`-run local numeric checks. Registers nothing; no verdict, band,
or arm ruling is banked by this document.**

**Date:** 2026-08-25 · **Grant:** row #188 item 2

**Question:** production's intake keeps only events with `distance_relative_error <
FRACTIONAL_LUMINOSITY_DISTANCE_ERROR_THRESHOLD = 0.10`
(`bayesian_statistics.py:386`, applied `:3790-3805` via `use_detection` `:5540-5554`, after
SNR≥20). Is this cut represented in the estimator's selection normalization, or is it an
unmodeled selection between generator and estimator (the D1 class)?

---

## 0. Verdict (draft)

**UNMODELED — one-sided, structurally so.** The cut is real, applied only on the
likelihood-intake side, and has **no counterpart anywhere in `p_det`/Σ**. This is not a
missing term that was overlooked in an otherwise-symmetric construction; it is
**structurally impossible to represent** in the current `p_det` pipeline, because that
pipeline never computes the quantity the cut is defined on (§1). It is the same D1-class
mechanism already caught, named, and measured **three independent times** in adjacent venues
in this repo (§3) — this is a fourth, direct confirmation, now traced to source in the
production code path itself rather than inferred from a mirror's behavior.

**Magnitude in production is small** (§3): on the two real production pools I could check
zero-compute, the cut removes **0.13%** (2/1590, seed 61000, this campaign) and **0.59%**
(20/3375, seed 600, independent commission red-team run) of the SNR≥20 population — three
orders of magnitude below the 41.8% (b0i venue) and ~10% (B-SEL mirror) figures already
banked for structurally different (donor-resampling-decoupled) harnesses. The two production
events actually dropped are marginal-SNR (22.3, 22.5 — just above threshold), non-catalogue
(dark-class) events, one of them at the largest luminosity distance in the pool.

## 1. Trace — does `p_det`/Σ know about the cut?

### 1a. `SimulationDetectionProbability` (`bayesian_inference/simulation_detection_probability.py`)

The module's own docstring states the acceptance definition it encodes, unambiguously:

> "Detection is *deterministic* optimal SNR (SNR = sqrt(⟨h|h⟩), no detector noise; the
> threshold is passed as `snr_threshold`)." (`simulation_detection_probability.py:7-8`)
>
> `d_hor_k = SNR_k * d_L_k / snr_threshold` — "the detection probability is *exactly* the
> survival function of the horizon distribution" (`:12-17`)

`grep` for `d_L_uncertainty`, `distance_relative_error`, `FRACTIONAL_LUMINOSITY`, or
`relative_error` anywhere in this 2000+-line file: **zero hits.** Every `n_detected` /
survival-table build (`:1943-1948`, `:1938`) thresholds purely on `d_hor >= dl_edges[...]`
(SNR-derived horizon), never on a distance-error ratio. `p_det` is a pure function of
`(d_L, M_z, [z, sky-band])` via SNR-horizon survival — there is no axis in the grid that could
even encode "was this synthetic injection's distance well-measured."

### 1b. The injection-pool generator (`main.py:injection_campaign`, feeds the pool above)

This is the deeper reason (1a) is true, not just a coincidence of what got wired up:

> "Run SNR-only injection campaign for detection probability estimation. Draws EMRI events
> from the population model, **computes SNR (no Fisher matrix)**, and stores ALL events
> (detected and undetected) to a per-task CSV file." (`main.py:915-918`)

The injection pool **never computes a Fisher matrix**, hence never computes
`d_L_uncertainty` (which requires it — `datamodels/detection.py:99,134-137`: `d_L_uncertainty
= sqrt(Γ⁻¹_{d_L,d_L})`, the CRB covariance element). `_INJECTION_COLUMNS`
(`main.py:862-884`) has no distance-error field. **The cut cannot be represented in the pool
even in principle** without a redesign (adding Fisher computation to every injection draw —
the exact cost the injection campaign is built to avoid, since it needs O(10⁴-10⁵) draws per
h/venue and the CRB Fisher matrix is the expensive step in the whole pipeline).

### 1c. The likelihood-intake side (`bayesian_inference/bayesian_statistics.py`)

Confirmed independently at `:3790-3805`:

```
n_before = len(self.cramer_rao_bounds)
self.cramer_rao_bounds = self.cramer_rao_bounds[self.cramer_rao_bounds["SNR"] >= SNR_THRESHOLD]
...
for index, detection in self.cramer_rao_bounds.iterrows():
    detection = Detection(detection)
    if use_detection(detection) is False:
        self.cramer_rao_bounds.drop(index, inplace=True)
```

`use_detection` (`:5540-5554`) is exactly `distance_relative_error < 0.10`. This runs
**after** the SNR cut, on the **real per-event Fisher-derived** `d_L_uncertainty` (not a
model value), and it is the only place in the whole evaluate() path this quantity gates
anything. `grep` confirms `FRACTIONAL_LUMINOSITY_DISTANCE_ERROR_THRESHOLD` has exactly 3
production-code occurrences: the constant (`:386`), the log message (`:3804`), and
`use_detection` (`:5549`) — none inside any Σ/β_G/D̃^φ/B_num construction function
(`grep -n "detection_probability\." bayesian_statistics.py` — 17 call sites, all
`detection_probability_{with,without}_bh_mass_interpolated*` / `_get_or_build_grid`, i.e. all
routed through the SNR-only object from §1a; none guarded by the distance-error threshold).

**Conclusion of (1):** the generator (injection pool → `p_det` → every Σ/β_G/D̃^φ term) and
the estimator's own data intake apply **different acceptance definitions** — SNR-only vs.
SNR-AND-distance-error — and nothing in the code brings them into agreement. This is the D1
class by definition: a selection criterion applied on one side of the generator/estimator
boundary and invisible to the other.

## 2. Do the Σ chains and S̄_φ/S_4D tables inherit this?

Yes, unconditionally — they have no alternative source of `p_det`. Every consumer
(`beta_G`/`beta_Gbar`, `D_h`/`D_tilde_phi`, `B_num`/`B_num_wbh`, the z-resolved and
z×M-resolved with-BH survival tables) is built by calling the **same**
`SimulationDetectionProbability` instance constructed once per `evaluate()` run
(`bayesian_statistics.py:3817-3835`) and threaded through as `detection_probability` to every
downstream integral. Since §1a shows that object is SNR-only by construction, **all of Σ is
SNR-only** — the distance-error cut cannot leak in through any of these paths because none of
them re-derive acceptance from anything other than `p_det`.

## 3. Magnitude — production's real event intake, and the analog venues already on record

### 3a. Zero-compute measurement on THIS campaign's own production pool (seed 61000)

```
total rows 1590, SNR>=20: 1590, pass distance-error cut: 1588, removed: 2 (0.126%)
dropped: dL=1.700 Gpc, SNR=22.35, rel=0.1065, in_catalog=False
         dL=7.336 Gpc, SNR=22.53, rel=0.2390, in_catalog=False (== the pool's max distance)
kept population: rel mean 0.0355, median 0.0373, max (surviving) 0.0993 (right at the boundary)
```
(computed directly from `results/campaign51_20260728/realistic_20260729/seed61000/prepared_cramer_rao_bounds.csv`,
`d_L_uncertainty = sqrt(delta_luminosity_distance_delta_luminosity_distance)` per
`datamodels/detection.py:134-137` — this column is already the CRB covariance element, not a
raw Fisher entry, so no matrix inversion is needed to reproduce the cut exactly.)

### 3b. Independent confirmation on a separate production dataset (seed 600, commission red-team)

> "Loaded 3375 detections; SNR≥20 keeps all 3375; d_L-relative-error<0.1 quality filter →
> 3355 events." (`results/commission_20260701/redteam/crux_realdata.md:55`) — **20/3375 =
> 0.59% removed.**

Both real production pools land in the **same tiny-but-nonzero regime** (0.1-0.6%), and both
dropped populations skew toward marginal-SNR, larger-distance, non-catalogue events — exactly
what the physics predicts: `d_L_uncertainty/d_L` for an EMRI's extrinsic parameters scales
roughly ∝ 1/SNR at fixed sky/inclination geometry, so events sitting just above the SNR≥20
floor are the ones most likely to cross the 10%-relative-error line, and that population is
disproportionately dark-class (no in-catalog host) simply because dark hosts extend to larger,
harder-to-localize distances in this population model.

### 3c. Why this is orders of magnitude larger in the harnesses already on record

The **b0i identity venue** measured **41.8%** removed (1397/2400 fleet rows;
`CLAIM_B0_FINITE_MOMENT_20260824.md:24-30`), and the **B-SEL production-calibration mirror**
measured **~10%** removed (`n_eff` 180/200;
`results/prod2d_closure_20260818/PREREGISTRATION_1D_CORRESPONDENCE.md:360-366`). Both of
those venues assign each drawn/synthetic host a **resampled donor Fisher row** (SNR-weighted
from the real production pool, but geometrically decoupled from that host's own true
distance/z) rather than computing that host's own Fisher matrix. That decoupling is exactly
what inflates the removal rate: it breaks the SNR↔distance-error correlation that keeps
production's own removal rate near-zero. This is a coherent, already-documented mechanism, not
a discrepancy needing new explanation — it is stated explicitly in the b0i finding itself:

> "In production the donor pool is post-filter at its own distances, so the filter is nearly
> inactive there; in the deep B-SEL venue it removes ~10% ...; in the shallow catalogue-class
> b0i venue it removes 41.8%." (`CLAIM_B0_FINITE_MOMENT_20260824.md:179-182`)

### 3d. Direction — already measured once, directly, in an analog venue (not yet in production itself)

The **only direct measurement** of which class the cut removes, done properly (not by
hand-wave), is D-1 (`PREREGISTRATION_1D_CORRESPONDENCE.md:492-513`, B-SEL mirror, seed 900101):
surviving events sit at **systematically higher z** than the model's assumed detected-dark
density predicts (CDF gap 0.079 > the 0.05 mirror-match tolerance) — i.e. **the donor-row
resampling plus the quality filter preferentially remove low-z events**, leaving an excess of
high-z events relative to what `p_det` assumes. That specific excess-high-z-vs-model pattern
has separately, and repeatedly, been tied to a **low** posterior rail in this codebase:

> "the general mechanism that an excess of high-z events relative to the model's assumed
> detected distribution rails the posterior low — which D-1 has now demonstrated a THIRD
> time" (`PREREGISTRATION_1D_CORRESPONDENCE.md:517-519`)

Chaining these two established results gives a directional hypothesis for production: **if**
the same low-z-preferential removal pattern holds on production's own (much smaller) dropped
set, the missing normalization term would push h **low**. But this chain is borrowed from the
donor-resampled mirror, and (3a)'s n=2 production sample is far too small to confirm or refute
the z-direction directly (one of the two dropped production events is a moderate-z, one is the
single farthest event in the pool — consistent with, but not proof of, the same pattern at
2 events). **Flagging this explicitly: the direction claim is INFERRED by analogy, not
measured in production.**

### 3e. A related but structurally distinct gap: the canonical coverage harness doesn't reach this mechanism at all

`validation/pp_coverage.py` (G4b, the canonical P-P/coverage calibration tool) has **zero**
references to `FRACTIONAL_LUMINOSITY_DISTANCE_ERROR_THRESHOLD`, `use_detection`,
`d_L_uncertainty`, or `SNR` — it is a simplified analytic-σ synthetic-universe harness with no
per-event Fisher/SNR concept at all. So this is not the "SHARED-SILENTLY, coverage-invisible"
case either (that would require the coverage tool to apply the *same* cut on its synthetic
side and thereby hide the mismatch): it simply doesn't model this axis in either direction.
The mirror harnesses that *do* reach Fisher-level granularity (b0i, B-SEL) have already
demonstrated the mismatch is **visible** when tested properly (D-1's CDF-gap failure,
`:499`) — so this is not a defect current tooling is blind to; it is a defect current tooling
has already caught, three times, just never before traced to its origin in the production code
path itself (§1) or measured on production's own real intake (§3a-b).

## 4. What would refute this

- If a future refactor adds an in-`p_det` distance-quality term (e.g. thresholding injections
  on a *modeled* σ_dL/d̂ rather than a real per-injection Fisher value — plausible since
  σ_dL/d̂ has a known approximate SNR-scaling), the "cannot be represented" claim in §1b would
  need revisiting; as of this read, no such term exists anywhere in `simulation_detection_probability.py`.
- If someone shows the 2/1590 and 20/3375 production numbers are unrepresentative outliers
  (e.g. a deeper future catalogue pool has SNR≥20 events routinely landing near the 10%
  distance-error boundary), the "small in production" magnitude claim would need updating —
  the mechanism itself would be unchanged, only its size.
- The z-direction claim (§3d) is explicitly NOT refuted-or-confirmed here; it is borrowed by
  analogy from a structurally different (donor-resampled) venue. A direct measurement on
  production's own dropped set (below) would settle it.

## 5. Cheapest decisive measurement

Pool the dropped-event diagnostics across **all** banked production `prepared_cramer_rao_bounds.csv`
seeds in this campaign (the same one-line computation as §3a, done once per seed, zero
