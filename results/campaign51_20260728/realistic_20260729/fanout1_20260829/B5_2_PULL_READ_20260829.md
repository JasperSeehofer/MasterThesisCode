## 1. L9 — what `BH_MASS_ERROR` actually is, from code (answers the docket's inconsistency)

the 0.55-dex R&V15 intrinsic scatter is "the DOMINANT term in `BH_MASS_ERROR`"; B8.1 §0

**Resolution, from code + commit history:**

1. `darksiren_emri/galaxy_catalogue/handler.py:1446-1459`
   (`_empiric_stellar_mass_to_BH_mass_relation`):
   ```python
   BH_mass = np.exp(alpha + beta * np.log(stellar_mass / 10))
   BH_mass_error = BH_mass * np.sqrt(
       sigma_int**2 + d_alpha**2
       + (np.log(stellar_mass / 10) * d_beta) ** 2
       + (beta / stellar_mass * stellar_mass_error) ** 2
   ```

## 2. Mirror-generator correspondence — how injected mass ties to host catalogue mass

**Fleet under test:** `p3_2d_fleet_20260825` (`bc_9001{01..24}_work`, `host_mode=
"catalogue_selected_2d"`, `results/campaign51_20260728/realistic_20260729/p3_2d_fleet.py:421`)
— the SAME 24-arm/2261-event basis `b5_window_count.py` uses (verified: `catalogue_md5`
and fleet row counts re-checked in this run, see `b5_pull_read.json:provenance`).

`darksiren_emri/validation/correspondence_1d.py:1736-1739`
(`_draw_2d_accepted_latents`, the `"catalogue_selected_2d"` generative step,
`PREREGISTRATION_P3_2D_20260825.md` §2(ii)):

```python
# Latent source-frame mass: M ~ N(host_M_eff, host_M_error) (the gaussian p_gal branch,
# Eddington-shifted mean -- mirrors bayesian_statistics.py:6223-6231/:6319-6320).
host_m = pool.M[host_idx_batch]
host_m_error = pool.M_error[host_idx_batch]
m_eff = _eddington_shifted_host_mass_batch(host_m, host_m_error)
...
m_true_batch = m_eff + sigma * rng.normal(size=batch)
```

with an unconditional **`M_true > 0`** rejection (`correspondence_1d.py:1654,1780`,
"DEFECT 1 repair, PA-2D-10" — any non-positive draw is redrawn, never floor-clipped).
**The injected mass IS tied to the host's own catalogue `BH_MASS`/`BH_MASS_ERROR`** — this
rules out hypothesis 2 (injected M unrelated to host mass) outright, the correspondence is
direct and by construction — **but the tying law is a linear-space Gaussian (truncated at
zero), not a log-normal**. `BH_MASS_ERROR` is used here as a **linear** 1σ (the draw is
`host_M + BH_MASS_ERROR · Z`), while the mass WINDOW filter (§2 of
`PHYSICS_CHANGE_MASS_WINDOW_GEOMETRY_20260829.md`) treats the SAME `BH_MASS_ERROR` as a
**log-space** σ (`σ_lnM = BH_MASS_ERROR/BH_MASS`, per §1 above). At small CV these two
usages agree to `O(CV²)` (§5.3 of the physics-change doc); at the fleet's actual median
`CV ≈ 1.02` they do not — a linear Gaussian with `CV~1` is asymmetric once the `M>0`
truncation removes the far left tail (any draw `Z < -1/CV` is rejected, but the right tail
is unbounded), which is EXACTLY what a symmetric log-window keyed to a Gaussian-tail table
cannot represent, regardless of which `σ_lnM` ratio is chosen. `M_z_true = M_true·(1+z_true)`
is what is passed to the EMRI simulator (`correspondence_1d.py:1744`) and lands, essentially
unperturbed by the near-exact GW mass measurement (§3), in the fleet's `prepared_
cramer_rao_bounds.csv` `M` column that `b5_window_count.py`/this script read as `M_z`.

## 3. The pull read

**Method** (script: `b5_pull_read.py`, this directory). Per event with a valid catalogued
true host (`in_catalog` and `0 ≤ host_galaxy_index < n_pruned`; **all 2261/2261** fleet
events qualify — the `"catalogue_selected_2d"` draw law guarantees an in-catalogue host by
construction, unlike B2.1's outside-cone class which is a *different* fleet/mechanism, L3):

```
x       = ln( M_z / (1+z_host) ) − ln( BH_MASS_host )        [z_host = host's OWN catalogue z]
CV      = BH_MASS_ERROR_host / BH_MASS_host
σ_def1  = CV                              ("ratio" == "ln-space σ directly", §1)
σ_def2  = ln(1 + CV)
σ_gw    = M_z_sigma / M_z                 (the window's own GW-side small-error correspondence)
pull_i  = x / σ_i
```

`z_host` is the host's own catalogue redshift (`cat.redshift[host_galaxy_index]`), not the
event's kernel-smeared drawn `z_true` — the two differ by a median `|Δz| = 0.0239` (p95
`0.072`, {source: `b5_pull_read.json:pooled.abs_dz_host_minus_ztrue_median/p95`, date:
2026-08-29}), the expected photo-z-kernel smear, small relative to the mass-driven pull
below and not the object under test.

**Fleet median `CV = 1.0182`** (p10–p90 `0.804–1.479`) {source:
`b5_pull_read.json:pooled.CV_median/CV_p10_p90`, date: 2026-08-29} — this REFINES the
docket's own "median CV ≈ 0.86" estimate upward by ~19%; `CV` is not `≪1` under any
reading, so the "small-error correspondence" (§2 of the physics-change doc, valid to
`O(CV²)`) is not merely marginal, it is off by `O(1)`.

## 4. Which docket hypothesis does the pull support?

The docket posed three candidate explanations for the 78.9%-at-k=3 retention shortfall:

1. **"`BH_MASS_ERROR` understates the realized generator scatter."** — **Not supported as
   stated.** `BH_MASS_ERROR` (via `σ_def1`) is EXACTLY the linear-space σ the generator
   draws with (`m_eff + BH_MASS_ERROR·Z`, §2) — it is not an understatement of the
   generator's own scatter, it IS the generator's scatter, verbatim, on the linear side.
   The mismatch is not a magnitude error, it's a **shape** mismatch (linear vs log — see 3
   below).
2. **"Injected M is not tied to the host's catalogue mass (a population-vs-catalogue
   object)."** — **REFUTED directly from code** (§2): `M_true = m_eff + BH_MASS_ERROR·Z`
   is drawn FROM the host's own catalogue row, by construction, every single event
   (`n_events_valid_true_host = n_events_loaded = 2261`, no fallback to a population-level
   draw for the accepted class this fleet reports on).
3. **"Small-error correspondence `σ_lnM=BH_MASS_ERROR/BH_MASS` misapplied at CV≈0.86."**
   — **CONFIRMED, but the mechanism is more specific than a formula choice.** The measured
   median CV is **1.02**, not `≪1`; neither candidate `σ_lnM` (ratio or `ln(1+CV)`) gets
   the log-window's `k=3` retention anywhere near 99.7% (78.8% / 74.9% respectively,
   pooled) — `ln(1+CV)` does not fix it, it makes it worse. The root mechanism (§2, §3): the
   generator draws a **linear**-Gaussian latent mass truncated at `M>0`; at CV~1 that
   truncation removes a substantial left tail while leaving the right tail unbounded, so
   `ln(M_true/M_host)` is NOT approximately Gaussian in log-space under any single `σ_lnM`
   choice — it is asymmetric (empirically: median pull ≈ −0.37 to −0.54, mean far more
   negative still, at −2.7 to −3.9, i.e. a small number of very-negative-pull events near
   the `M_true→0⁺` boundary drag the mean well past the median). **No `σ_lnM` redefinition
   closes this gap; only a log-normal (or otherwise `M>0`-native) latent-mass generative
   law would let a symmetric log-window's `2Φ(−k)` accounting apply.**

**Does the `ε = 2Φ(−k)` rationale hold for k=3's retention?** **No, not as a retention
statement.** `2Φ(−k)` (`wgeom_instrument.eps_log`, banked and G4-verified) is a
**single-candidate, CV-independent** statement about a symmetric log-normal population's
own tail mass — it is correctly derived and correctly measured (§6 item 3 of the
physics-change doc) for THAT object. It is **not** the same object as fleet-level
**true-host retention**, which additionally depends on (a) the true generative law's shape
(here: linear-Gaussian-truncated, not log-normal) and (b) the specific `CV` realized by
each host (here: median 1.02, not the `ε₀=1` normalized unit the `2Φ(−k)` table assumes).
No `σ_lnM` definition tested here makes k=3 retain ≈99.7% of true hosts; the retention
number that k=3 actually delivers on this fleet (**78.9%**, `b5_window_count.json`) is the
one to carry into any registration, not `1 − 2Φ(−3) = 99.73%`.
